## 2. Открытие, которое сильнее всего меняет наш код: `mp.makeEventSource`

Сегодня **три наших сервиса опрашивают состояние каждые 2 секунды** — `death-service.js` (ловит HP≤0 и всплески урона), `player-panel-service.js` (показатели панели) и `voip-service.js` (громкость по расстоянию). Это писалось в предположении, что альтернативы нет.

Она есть. `mp.makeEventSource(имя, телоФункции)` внедряет кусок JS в клиент, который выполняется в игровом цикле и вызывает `ctx.sendEvent()`, когда захочет; сервер получает это через `mp._имяСобытия = (pcFormId) => {}`.

```js
// Пользовательское имя ОБЯЗАНО начинаться с подчёркивания.
mp.makeEventSource("_onLocalDeath", `
  ctx.sp.on("update", () => {
    const pl = ctx.sp.Game.getPlayer();
    const isDead = pl.getActorValuePercentage("health") === 0;
    if (ctx.state.wasDead !== isDead) {
      if (isDead) ctx.sendEvent();
      ctx.state.wasDead = isDead;
    }
  });
`);
mp._onLocalDeath = (pcFormId) => { /* ... */ };
```

Этот пример буквально взят из официальной документации — и это в точности случай нашего `death-service`.

**Что это решило бы:**
- Смерть определяется в тот кадр, когда происходит, а не с задержкой до 2с. В RP-сцене 2 секунды задержки перед входом в `DOWNED` — это разница между работающей и неработающей сценой.
- Конец `checkDamageSpike` как эвристики: вместо вывода урона из падения HP между тиками клиент сообщает о событии.
- Затраты CPU сервера перестают расти линейно с числом подключённых игроков.

**Честная оговорка:** сниппет выполняется на клиенте — территории недоверия (см. `MODS_AND_GAMEMODE_CONTRACT.ru.md`). Событие оттуда — это *подсказка*, а не доказательство: сервер всё равно обязан проверять. Для смерти это приемлемо (худший случай — кто-то подделает собственную смерть). Для выдачи предмета или золота — нет.

## 2.5 Недостающий источник: `misc/tests/` в upstream

Документация в `docs/` описывает пять методов `mp`. Реальный API гораздо больше, и место, где он появляется **работающим**, — это папка `misc/tests/` в upstream: девять интеграционных тестов, которые выполняются против настоящего сервера.

Это делает их надёжнее любой документации: это код, который обязан проходить.

```bash
gh api repos/skyrim-multiplayer/skymp/contents/misc/tests --jq '.[].name'
```

### Что они решили за нас

**1. Формат `self` у Papyrus — решён.** Все девять тестов используют `{ type: 'form', desc: mp.getDescFromId(id) }`, никогда сырой FormID, в том числе для *аргументов*, которые являются ссылками:

```js
mp.callPapyrusFunction("method", "ObjectReference", "RemoveAllItems",
    { type: "form", desc: mp.getDescFromId(actorId1) },
    [{ type: "form", desc: mp.getDescFromId(actorId2) }, false, false]);
```

В этом проекте было 22 вызова с сырым FormID. Все переведены — см. `core/papyrus.js` (`actorRef`/`baseRef`).

Там же видно различие `form` и `espm`: актёр — это `form`, а Gold001, добавляемый ему в инвентарь, — `espm`.

**2. `mp.onDeath` существует и приносит убийцу.**

```js
mp.onDeath = (actorId, killerId) => { /* killerId равен 0, когда автора нет */ };
mp.onRespawn = (actorId) => {};
```

Наш `death-service.js` опрашивает каждые 2с, читая `getActorValue('Health')`, а боевая документация этого проекта в своё время зафиксировала, что «надёжного хука о том, кто кого атаковал, нет». Для момента смерти — а это и есть то, что важно против RDM, — **он есть**. Из-за этого `logDeathContext` по близости оказывается излишним приближением для атрибуции.

**3. Другие хуки и вызовы, подтверждённые тестами:**

| | |
|---|---|
| `mp.onActivate = (target, caster) => {}` | Кто-то использовал объект/актёра |
| `mp["onPapyrusEvent:OnItemAdded"] = fn` | Произвольное событие Papyrus, по имени |
| `mp.createActor(profileId, pos, angleZ, cellOrWorld)` | Создать актёра со стороны сервера |
| `mp.set(id, "isDead", true)` | Убить напрямую, без Papyrus |
| `mp.set(id, "inventory", {entries:[{baseId,count}]})` | **Записать весь инвентарь разом** |
| `mp.get(id, "inventory").entries` | Прочитать инвентарь |
| `mp.set(id, "spawnDelay", 0)` | Управлять задержкой респавна |
| `mp.get(id, "spawnPoint")` | Точка спавна размещённого актёра |

Пара `get/set` для `inventory` примечательна: сегодня `inventory-service.js` синхронизирует предмет за предметом через `AddItem`. Один `set` был бы проще и атомарнее на стороне клиента.

## 2.6 Личность и вход: как SkyMP на самом деле разрешает `profileId`

Источник: `skymp5-server/ts/systems/login.ts` и `skymp5-server/ts/settings.ts`.

Это отвечает на открытый вопрос «откуда игровой режим знает, кто игрок» — пункт 1.6 нашего `QA_REPORT_2026-08.ru.md`.

**Есть два режима, и разница в них — это всё:**

**`offlineMode: true`** — клиент присылает `gameData.profileId`, и сервер **верит**. Это лабораторный режим. Любой правит `skymp_config.json` и становится другим человеком.

**`offlineMode: false`** (по умолчанию) — клиент присылает `gameData.session`, и сервер **разрешает сессию через мастер-API**:

```
GET  {master}/api/servers/{masterKey}/sessions/{session}
  →  { user: { id: number, discordId: string } }
```

`profileId` теперь приходит от мастера, а не от клиента. **Именно здесь личность становится доверенной.**

Стандартный `master` — `https://gateway.skymp.net`, но это просто строка в `server-settings.json`.

### Путь к нашему пункту 1.6

У нас уже есть всё, что нужно этому эндпоинту: OAuth Discord, вайтлист и таблица `launch_tickets`, созданная в миграции v6. **`apps/web` может быть нашим мастер-API** — это всего один эндпоинт:

1. `apps/web` реализует `GET /api/servers/:masterKey/sessions/:session`, разрешая тикет в `{ user: { id: accountId, discordId } }`.
2. `server-settings.json` указывает `master` на нашу панель и задаёт `masterKey`.
3. `offlineMode: false`.
4. Лаунчер уже пишет `config.session` — начинает писать туда тикет, выпущенный панелью.

После этого `whitelist.js` перестаёт доверять `profileId` клиента, и менять в нём ничего не нужно: приходящий `profileId` **и есть** проверенный `accountId`.

Это заметно проще, чем `/internal/session/resolve`, который мы построили в `apps/game-api`, и использует уже существующий механизм SkyMP вместо параллельного.

### `mp.onLoginAttempt`

`login.ts` вызывает, если он определён:

```js
mp.onLoginAttempt = (profileId) => boolean;  // false отклоняет подключение
```

Это правильная точка для вайтлиста и банов — клиент получает `loginFailedBanned`. Сегодня мы делаем это опросом подключений + `mp.kick` постфактум.

### Нативный `discordAuth` на сервере

`server-settings.json` принимает:

```json
{
  "discordAuth": {
    "botToken": "...",
    "guilds": [{
      "guildId": "...",
      "banRoleId": "...",
      "hideIpRoleId": "...",
      "eventLogChannelId": "..."
    }]
  }
}
```

Тогда сервер сам: требует, чтобы игрок был в Discord, отказывает тем, у кого роль бана, скрывает IP у тех, у кого `hideIpRoleId`, и **пишет входы в канал**. Роли Discord становятся доступны в игровом режиме через свойство `private.discordRoles`.

Часть этого мы построили в `apps/bot-discord`. Стоит сравнить, прежде чем вкладываться в своё дальше.

Замечание: свойства с префиксом `private.` клиенту не видны.

## 3. Инструменты разработки, которые уже есть и которыми мы не пользуемся

Эти три экономят больше всего времени, и ни один не требует писать код:

### DevTools Chromium на порту 9000
Встроенный браузер отдаёт удалённые DevTools. Откройте **`localhost:9000`** в настоящем Chrome — и у вас есть консоль, инспектор и точки останова для нашего внутриигрового интерфейса.

Сегодня `skymp/ui/index.html`, `player-panel.js` и `player-panel.css` отлаживаются **вслепую**. Это меняется одним URL.

### Живая перезагрузка интерфейса через порт 1234
Если на той же машине на порту 1234 работает dev-сервер WebPack, сервер SkyMP **проксирует запросы интерфейса на него**. То есть можно править CSS и JS интерфейса, не перезапуская сервер и не переподключая клиент.

### Драйвер базы `file` для тестов
`databaseDriver: "file"` хранит мир в каталоге, без MongoDB. Именно это уже использует наш `server-settings.local.example.json` — стоит знать, что есть ещё `zip` (то же самое в одном файле, удобно для снимка перед разрушительным тестом) и `mongodb` для продакшена.

## 4. Бой: исправление прежнего понимания

Ранее в этом проекте был зафиксирован вывод, что «надёжного хука о том, кто кого атаковал, не существует». Здесь нужен нюанс:

**Пакет OnHit существует** и он богатый (`docs_onhit_and_damage.md`):

```c++
uint32_t aggressor;   bool isBashAttack;   bool isHitBlocked;
bool isPowerAttack;   bool isSneakAttack;  uint32_t projectile;
uint32_t source;      uint32_t target;
```

Чего **нет** — так это его проброса в JS-игровой режим: issue #1338 просила об этом и была закрыта как won't fix. Данные лежат в C++, а не в нашем слое.

Два выхода, оба рабочие:
1. **`makeEventSource` на клиенте**, слушающий событие попадания Skyrim Platform и отправляющий `{aggressor, target}` на сервер. Дёшево и лучше близости, которой мы пользуемся сегодня, — но это по-прежнему говорит клиент.
2. **`IDamageFormula` на C++** — SkyMP предоставляет интерфейс именно для того, чтобы кастомные серверы переопределяли формулу урона. Вот там данные действительно надёжны, но нужна сборка сервера на C++.

**Это перестало быть теорией.** RP-сервер Red House реализовал вариант 1, и код открыт — см. `REFERENCE_STUDY_SKYMP_RED_HOUSE.md` §4.1 (на португальском). Там же две детали, которые стоили бы часов отладки (`0x14` локального игрока и обязательное преобразование FormID), и предупреждение о производительности, которое касается и нас.

Пока не сделано ни одно из двух, `/iniciar` + `checkDamageSpike` — это то, что у нас есть: доказательство по близости, а не атрибуция.

## 5. Осторожно с портами

| Порт | Кто использует |
|---|---|
| 7777/UDP | SkyMP, синхронизация (по умолчанию) |
| 3000/HTTPS | Интерфейс встроенного браузера — **не настраивается** |
| 9000 | DevTools встроенного Chromium |
| 1234 | Dev-сервер WebPack (живая перезагрузка интерфейса) |
| 3001 | `apps/web` |
| 3002 | `apps/bot-discord` |
| 7758 | `apps/game-api` |
| 7778 | VOIP (`VOIP_PORT`) |

⚠️ **Порт интерфейса — это `основной порт + 1`, когда основной нестандартный.** В нашем `apps/launcher/.env.example` стояло `VITE_SERVER_PORT=7757`, а в `skymp/config/server-settings.*.example.json` — `"port": 7777`. Две проблемы:

1. Значения по умолчанию **не совпадали** — клиент пробовал бы 7757, пока сервер слушает 7777.
2. Если стандартизоваться на 7757, интерфейс уйдёт на **7758 и столкнётся с `apps/game-api`**.

**Решено 05.08.2026:** лаунчер перешёл на 7777 (по умолчанию и в примерах), в согласии с `server-settings`. Предупреждение осталось в `.env.example`: смена основного порта на нестандартный сдвигает интерфейс и может столкнуться с `game-api`.

## 6. Что мы искали и чего не существует

- **Публичной типизации TypeScript для API `mp` нет.** `skymp5-functions-lib` из upstream импортирует из `src/`, которого в репозитории нет — публичен только `index.ts`. Свою мы написали в `skymp/gamemode/types/mp.d.ts`.
- **Ни один другой RP-сервер не опубликовал свой игровой режим.** Три найденных активных форка — копии upstream без открытого RP-кода.
- **`skymp-ui-components`** (библиотека интерфейса организации) заброшена с 2020 года. Брать не стоит.
- **`sweettaffy-lib`** — это свод правил RP сервера SweetTaffy (на русском), а не код, но полезен как образец *проектирования* правил RP-сервера.
- **Релизы**: последний — `sp-v2.6-beta` от 2022 года. Проект развивается в ветке `main`, а не релизами. Фиксироваться на коммите, а не на теге.
